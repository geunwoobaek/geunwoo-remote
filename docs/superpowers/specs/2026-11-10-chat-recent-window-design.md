# 긴 채팅을 최근 부분만 먼저 보이기 설계

## 의도

메시지가 1만 개 넘게 쌓인 채팅을 폰에서 열면 15초쯤 빈 화면(빙글이)만 보이다가 마지막 답이 뜬다. 맥 백그라운드 세션 "SAP ERP 개발"(서버 메시지 10,501개)에서 확인했다. 원인은 네트워크가 아니라 앱 안 작업이다. 앱은 폰 DB에 받아 둔 그 세션의 메시지를 **전부** 읽어 화면용으로 정리한 뒤에야 첫 화면을 그린다.

사용자의 요구(2026-11-10): 긴 세션은 앱에서 해결한다. 열면 최근 부분만 보이고, 사용자가 무한 스크롤처럼 위로 더 올리면 그 이전이 더 보인다.

이 문제는 백그라운드 세션만의 것이 아니다. 일반 세션도 오래 쓰면 똑같이 길어지고, 처음 연결할 때 맥 쪽에서 최근 부분만 올리더라도 폰으로 몇 주 쓰면 다시 길어진다. 그래서 앱의 채팅 화면이 고친다.

## 목표

1. 채팅을 열면 메시지가 몇 개든 최근 약 300개로 첫 화면을 그린다. 1만 개짜리 채팅도 300개짜리처럼 빨리 열린다.
2. 사용자가 맨 위까지 올리면 그 이전 약 300개를 덧붙인다. 다시 맨 위에 닿으면 또 덧붙인다. 대화의 처음까지 계속된다.
3. 덧붙일 것이 폰 DB에 있으면 DB에서, 다 떨어지면 서버에서 가져온다.
4. 창 경계에서 화면이 깨지지 않는다. 도구 호출이 영원히 "실행 중"으로 남거나, 엉뚱한 옛 권한 카드·하위 에이전트 줄이 맨 위에 뜨지 않는다.

## 하지 않을 것

- **백그라운드 세션의 맥 기록 중 서버에 아직 없는 부분 불러오기.** 거울은 처음 연결할 때 맥 기록의 최근 부분(약 300줄, 최대 1000줄)만 서버에 올린다. 그래서 백그라운드 세션 채팅은 위로 올려도 거기서 멈춘다. 그보다 오래된 맥 기록까지 보이게 하려면 거울이 "더 오래된 기록 보내기" 요청을 받아야 하는데, 나중에 올린 옛 기록이 더 큰 서버 순번을 받게 되어 앱의 순번 기반 페이징 전제가 깨진다. 따로 다룬다.
- **서버 수정, 서버의 옛 메시지 지우기.** 기록은 그대로 둔다.
- **채팅 밖 화면(세션 목록, 파일 화면)의 동작 변경.** 단, 아래 "메시지 상세 화면"은 창 밖 메시지를 열 수 있어야 한다.

## 실패로 보는 것

- 창 경계에서 도구 줄이 영원히 빙글이로 남는 것.
- 창이 넓어질 때 이미 보던 메시지가 사라지거나 순서가 바뀌는 것, 보던 위치가 튀는 것.
- 사용자가 올리지 않았는데 이전 기록을 처음까지 줄줄이 불러오는 것.
- 새 메시지가 올 때마다 화면 정리를 처음부터 다시 하는 것.

## 지금 구조 (코드로 확인)

경로 앞부분 `H/` = `packages/happy-android/app/src/main/kotlin/com/slopus/happy/`.

- **받아 오기.** `H/sync/MessageSync.kt`. 열 때 서버에서 최신 100개(`before_seq`)를 받고(228행), 폰 DB가 뒤처져 있으면 500개씩 앞으로 따라잡는다(234~244행). 더 오래된 것은 `loadOlder`(261~287행)로 100개씩 받는다. 열 때마다 최대 5번(500개) 미리 받아 둔다(`prefetchOlder`, 295행).
- **폰 DB.** 한 세션의 메시지는 항상 끊김 없는 순번 구간(`messages_oldest_seq..messages_seq`)으로 저장된다. `HappyStore.messages(sessionId, limit)`(HappyStore.kt 441행)는 이미 `limit`을 받지만 기본값이 전부다.
- **화면 정리.** `MessageSync.messages()`(112행)가 바뀔 때마다 DB에서 그 세션 메시지를 전부 읽는다. `ChatFeed`(H/chat/ChatFeed.kt)의 `ChatReduction.apply`(106행)는 처음 보는 메시지만 정리하지만, 처음 열 때는 전부를 정리한다. 이미 정리한 메시지가 목록에서 하나라도 빠지면 전부를 처음부터 다시 정리한다(116~123행).
- **위로 올리기.** `ChatList`(H/ui/chat/ChatList.kt)는 `reverseLayout` 목록이다. 맨 위 근처(`nearOldest`, 251행)에 오면 `loadOlder`로 서버에서 이전 페이지를 받는다(288행). 그런데 `nearOldest`는 접힌 작업 묶음 기준으로 재므로, 메시지가 많이 접히면 계속 참으로 남는다. 페이지가 도착할 때마다 다시 다음 페이지를 부른다. 이 연쇄가 폰 DB에 1만 개가 다 쌓인 이유로 보인다(기기에서는 아직 확인하지 않았다).

## 접근

| 방법 | 내용 | 판단 |
|---|---|---|
| A. 읽는 쪽에 하한 순번 두기 (선택) | 채팅 화면이 DB에서 "하한 순번 이상"만 읽는다. 하한은 열 때 최근 약 300개 지점에서 정하고, 위로 올릴 때만 내려간다. | 받기·저장은 그대로라 바꿀 곳이 좁다. 이미 쌓인 1만 개 채팅도 바로 빨라진다. |
| B. 폰 DB에 최근 것만 남기기 | 오래된 메시지를 폰 DB에서 지우고, 올리면 서버에서 다시 받는다. | 오프라인에서 옛 기록이 안 보이고, 끊김 없는 순번 구간 전제를 건드린다. |
| C. 맥 쪽에서만 줄이기 | 거울이 올리는 양만 줄인다. | 이미 했다. 일반 세션과 오래 쓴 세션은 못 막는다. |

## 설계

### 창(window)

- 열린 채팅마다 **하한 순번(floor)**을 하나 둔다. 화면은 폰 DB에서 `seq >= floor`인 메시지만 읽는다.
- **하한은 내려가기만 한다.** 새 메시지는 하한 위에 붙으므로 그대로 들어온다. "최신 N개"처럼 미끄러지는 창은 새 메시지마다 맨 아래 메시지 하나가 빠져, `ChatFeed`가 전부를 다시 정리하게 된다(116~123행). 그래서 쓰지 않는다.
- **처음 하한:** 최신에서 300번째 레코드(폰 DB의 메시지 한 줄)를 기준점으로 잡고, 그 앞의 가장 가까운 사용자 입력(한 차례의 시작)까지 내려간다. 단, 최신에서 1000번째보다 더 내려가지는 않는다. 그 안에 사용자 입력이 없으면 기준점 뒤의 첫 에이전트 레코드부터 시작한다(결과만 있고 호출이 없는 도구 줄을 피하려고). 300개 이하인 채팅은 전부 읽는다. 맥 거울의 업로드 범위(`uploadStart`, runClaudeAgentMirror.ts 124~163행)와 같은 규칙을 레코드에 적용한 것이다.
- **사용자 입력의 뜻:** 정리 전 단계(`ChatNormalizer`)가 사람의 글(사용자 텍스트 메시지)로 분류하는 레코드다. 폰에서 보낸 말과, 맥 기록에서 올라온 사람의 입력이 여기에 든다. 도구 결과, "[Request interrupted…]" 같은 중단 표시, 하위 에이전트(sidechain) 레코드는 들지 않는다. Codex 등 다른 에이전트 세션도 같은 분류를 쓴다. 하한 계산은 열 때 최대 1000개만 분류하므로 비용은 작다.
- **이유:** 한 차례의 시작에서 자르면 도구 호출과 그 결과가 창 경계에서 갈리지 않는다. 결과만 창 안에 있고 호출이 밖에 있으면 정리 단계가 결과를 버리고(ChatReducer.kt 3단계), 나중에 호출이 들어오면 그 줄이 영원히 "실행 중"으로 남는다.

### 위로 올리기

- 사용자가 맨 위에 닿으면 하한을 다시 약 300개 아래로 내리고, 같은 규칙으로 한 차례의 시작에 맞춘다.
- 내릴 것이 폰 DB에 있으면 DB에서만 읽는다. 하한이 폰 DB의 가장 오래된 순번에 닿았고 서버에 더 있으면, 그때 `MessageSync.loadOlder`로 서버에서 받는다. "더 있음" = `floor > 폰 DB 최저 순번` 또는 서버에 더 있음.
- 서버에서 받을 때는 한 번 맨 위에 닿은 것을 한 묶음으로 친다. 그 한 묶음 안에서 100개 페이지를 약 300개가 될 때까지, 또는 한 차례의 시작이 나올 때까지 받는다(최대 1000개). 이것은 연쇄가 아니다. 사용자가 맨 위에 한 번 닿을 때 한 묶음만 받는다.
- **연쇄 금지.** 한 번 맨 위에 닿으면 한 번만 덧붙인다. 덧붙인 뒤에는 사용자가 다시 맨 위에 닿아야 다음 것을 부른다. 지금의 `nearOldest` 연쇄(ChatList.kt 251·288행)를 이 규칙으로 바꾼다.
- 덧붙일 때 보던 위치는 그대로 둔다. 지금 `loadOlder`가 이미 하는 방식을 따른다.
- 열 때 서버에서 미리 받아 두는 것(`prefetchOlder`)은 폰 DB에만 쓰므로 그대로 둔다.

### 정리 단계(reducer) 경계 처리

한 차례의 시작에서 자르는 것으로 막히지 않는 세 가지를 따로 막는다.

1. **옛 권한 기록.** 세션 상태의 끝난 권한 요청(`completedRequests`) 중 짝이 되는 도구 줄이 없는 것은 0단계에서 가짜 도구 줄로 만든다(ChatReducer.kt 279~340행 부근). 창 시작 시각보다 오래된 요청은 만들지 않는다. 창이 내려가 진짜 도구 줄이 들어오면 지금처럼 2단계에서 합쳐진다.
2. **할 일·사용량 덮어쓰기.** 0.5단계의 "Context was reset", "Compaction completed"는 시각 확인 없이 최신 할 일과 사용량을 덮어쓴다(ChatReducer.kt 230~234행). 나중에 들어온 옛 묶음이 새 값을 덮지 않게, 다른 경로처럼 시각을 확인한다.
3. **창 밖에서 시작한 하위 에이전트.** 하위 에이전트를 띄운 Task 호출이 창 밖이면, 그 하위 대화의 첫 줄이 홀로 떨어진 줄로 보인다(ReducerTracer.kt). 한 차례의 시작에서 자르면 대부분 막힌다. 남는 경우가 화면에 어떻게 보이는지는 빌더가 확인한다. 고칠 필요가 있으면 하위 대화를 주인이 들어올 때까지 붙잡아 두는 기존 고아 처리(`processOrphans`)에 맞춘다.

### 메시지 상세 화면

`MessageDetailRouteScreen`(H/ui/files/FilesRoutes.kt 344~356행)은 `ChatFeed` 결과에서 메시지 id를 찾고, 없으면 뒤로 간다. 창 밖 메시지를 열 수 있어야 하므로 id로 직접 찾거나, 그 메시지까지 창을 내린다. 방법은 빌더가 고른다.

### 창의 수명

하한은 그 채팅 화면이 살아 있는 동안 유지된다. 메시지 상세 화면에 갔다 돌아오면 그대로다. 채팅을 나갔다가 다시 열거나 앱이 다시 시작되면 처음 하한(최근 약 300개)부터 다시 시작한다(나의 결정: 오래 올려 보던 위치를 기억하는 일은 드물고, 기억하면 다시 열 때 다시 느려진다).

### 먼저 잴 것과 합격선

- **합격선:** 메시지 1만 개짜리 채팅을 사용자 폰(갤럭시 S23 Ultra)에서 열 때 첫 화면이 2초 안에 뜬다. 맨 위에 닿아 한 묶음이 붙는 데 1초 안. 새 메시지가 올 때 화면이 멈칫하지 않는다.
- 15초가 어디서 쓰이는지 아직 재지 않았다. DB 읽기, 정리, 마크다운 변환, 화면 묶음 계산(ChatList.kt 278~286행) 중 무엇이 큰지 기존 기기 벤치(`androidTest/.../bench/ChatListBenchmark.kt`, `HeavyChat.kt`)로 먼저 잰다.
- 창 설계는 결과와 상관없이 맞다. 창을 넣은 뒤에도 합격선을 못 넘으면, 그때 가장 큰 병목(예: 300개 전체를 다시 묶는 화면 계산)을 이 작업 안에서 고친다.

## 시험

- **단위:**
  - `ChatFeedTest`: 하한이 내려가기만 하는지, 새 메시지가 와도 전부 다시 정리하지 않는지, 한 차례의 시작에 맞춰 자르는지, 도구 호출과 결과가 경계에서 갈리지 않는지.
  - `MessageSyncTest`: 위로 올리기가 폰 DB를 먼저 쓰고, 다 떨어졌을 때만 서버를 부르는지.
  - `ChatReducerTest`: 창 시작 전 권한 기록이 가짜 줄로 안 생기는지, 옛 묶음이 할 일·사용량을 덮지 않는지.
  - `WorkGroupsTest`: 사용자 입력 없이 시작하는 맨 위 차례도 깨지지 않고 그려지는지.
  - 메시지 상세: 창 밖 메시지 id로 열어도 뒤로 가지 않는지.
- **기기:** 일회용 세션으로 메시지 1000개 넘는 채팅을 만들어 연다. 첫 화면 시간, 맨 위로 올릴 때 한 번에 한 묶음만 붙는지, 위치가 튀지 않는지 본다. 사용자 세션은 열지 않는다. "SAP ERP 개발"에서의 확인은 사용자에게 부탁한다.

## 빌더에게 맡기는 것

- 하한 상태를 `ChatFeed`와 `MessageSync` 중 어디에 둘지.
- "맨 위에 닿음"을 재는 방법(접힌 묶음이 아니라 실제 목록 위치 기준).
- 메시지 상세 화면의 찾기 방법.
